# Five second-brain systems: what to borrow, and where a company brain begins

**Status:** Research evidence, not an approved specification or implementation request. **Reviewed:** 2026-09-29. **Method:** read project documentation and representative implementation at the pinned commits below; no third-party code, hosted services, or retrieval benchmarks were run. Source-code checks distinguish implemented mechanisms from prompt instructions and advertised behavior. Planning contract: version 1; installed catalog revision unknown.

## Starting point: our second brain

[`second-brain/SKILL.md`](../../skills/tools-and-research/second-brain/SKILL.md) already defines search → capture → compare → synthesize → check. [`sb.py`](../../skills/tools-and-research/second-brain/scripts/sb.py) already has an OKF v0.2 Markdown bundle, append-only source captures, immutable originals in `raw/`, editable canonical pages with compare-and-swap SHA-256 and archived revisions, atomic notes with supersession, generated navigational indexes, FTS5 search, `status`/`stale_after`/human verification, link/index drift checks, orphans, and near-duplicate detection. The `personal/` source area is read-only on ingestion. Do not reimplement these as if absent. In particular, do not change ordinary Markdown links to Obsidian `[[wikilinks]]`, turn FTS5 into an authoritative database, or add a second `syntheses/` folder. `lint` currently **reports** problems but returns 0; any future CI gate needs an explicit strict mode, not a silent behavior change. `capture` creates a new source entry each time; it has no same-content/revision detection. Search is page-level FTS5 without citation-aware chunk boundaries or answer-level evaluation.

The common core is **source → attributed, revisable synthesis → navigable wiki → bounded retrieval → maintenance**. Our existing skill already covers most of that. The biggest missing value is not another folder hierarchy or more slash commands; it is **measurable retrieval, operational provenance/freshness, and cheaper frictionless intake**. Links above identify repo-owned docs or code, not independent validation of vendor performance claims.

## Prioritized improvements to the personal skill

### A. Improve the workflow before adding infrastructure

1. **Make recall answer-shaped.** For a question, search a small set of pages, follow their source links, cite the specific source passages/pages adjacent to each material claim, expose `draft`/stale/unverified status, say when evidence is missing, and separate wiki evidence from model background knowledge. Our skill already says much of this for writes; its *answer* contract is less explicit. [second-brain-os retrieval guidance](https://github.com/undefined-ui/second-brain-os/blob/dcead4dff5cf305c2241d417360730f99fbf7279/docs/07-retrieval/README.md) makes this distinction central; [llmwiki search](https://github.com/lucasastorian/llmwiki/blob/aac3e6493306b7fff3b09cb181ca93918e93d0e6/mcp/tools/search.py) labels source matches separately from annotation matches. No new dependency.
2. **State capture completeness honestly.** In source frontmatter or the run report, distinguish full local text, bounded excerpt, and URL-only pointer; do not promote URL-only metadata as having been read. We already document this in prose; encode the distinction only where it prevents a real misuse. [obsidian-second-brain ingest](https://github.com/eugeniughelbur/obsidian-second-brain/blob/b0089f7666d0c1e3db41c9d587b6f3c997665235/commands/obsidian-ingest.md).
3. **Keep a small, explicit relation vocabulary** for *supported-by*, *contradicts*, *supersedes*, and optionally *part-of*, not a general inferred graph. First express the relation in nearby cited prose and ordinary Markdown links; add structured metadata only when graph queries need it. Don't type every link, force reciprocal links where they add no meaning, or silently turn inferred edges into facts. [second-brain-os typed links](https://github.com/undefined-ui/second-brain-os/blob/dcead4dff5cf305c2241d417360730f99fbf7279/docs/05-graphs/typed-links.md); [llm-wiki-agent graph labels](https://github.com/SamurAIGPT/llm-wiki-agent/blob/572c8eb06e7226567e55a9f186c0860d755a0d51/tools/build_graph.py).
4. **Target changing facts, not everything, for refresh.** On review, distinguish stable concepts from current prices, APIs, jobs, incidents or project status; ask whether to re-observe, keep a dated claim, or replace it with a live-system pointer. Don't blanket-stamp all notes with an arbitrary TTL or equate unavailable source with false claim. [COG memory hygiene](https://github.com/huytieu/COG-second-brain/blob/4cdb6015dc6eb66f74bac513856ff6446ecb5d1b/.claude/skills/memory-hygiene/SKILL.md); [obsidian-second-brain freshness policy](https://github.com/eugeniughelbur/obsidian-second-brain/blob/b0089f7666d0c1e3db41c9d587b6f3c997665235/references/freshness-policy.md). Existing `stale_after`/`verified` fields supply a start.
5. **Document the output of ingest.** A short report listing source capture, created/updated pages, links, conflicting claims, skipped material and open gaps prevents an agent from treating a partial ingest as complete. The current skill already asks to check evidence; this makes the result visible. [second-brain-os ingest](https://github.com/undefined-ui/second-brain-os/blob/dcead4dff5cf305c2241d417360730f99fbf7279/skills/second-brain-ingest/SKILL.md). Don't add a persistent report artifact for each ingest.

### B. Small deterministic tooling only for observed workflows

1. **Idempotent source capture / revision detection.** Hash source bytes or normalized extracted text (identify which), retain the original URL and retrieval time, and distinguish same content, changed content at the same source, and a different source. Keep old captures, link a new snapshot to its predecessor, and never overwrite handwritten originals. `sb capture` presently always creates a new source file; repeated fetches can create duplicates. [obsidian-second-brain ingest](https://github.com/eugeniughelbur/obsidian-second-brain/blob/b0089f7666d0c1e3db41c9d587b6f3c997665235/commands/obsidian-ingest.md). An identity design needs to account for two URLs with the same text and one URL changing over time; an aggressive URL normalizer can conflate distinct resources.
2. **A tiny retrieval eval before changing search.** Curate actual user questions with acceptable page paths and failure cases (synonyms, multilingual names, stale/deprecated notes); score FTS5 top-k and report misses. Optionally add title/alias boosts or source-versus-synthesis filtering if measured cases warrant them. The [obsidian-second-brain harness](https://github.com/eugeniughelbur/obsidian-second-brain/blob/b0089f7666d0c1e3db41c9d587b6f3c997665235/scripts/eval/retrieval_eval.py) reports recall@k/MRR; its [300-note synthetic corpus](https://github.com/eugeniughelbur/obsidian-second-brain/blob/b0089f7666d0c1e3db41c9d587b6f3c997665235/scripts/eval/BENCHMARK.md) improves paraphrase/multilingual recall with hybrid retrieval *there*, not automatically here. The eval does not establish answer correctness or citation faithfulness.
3. **Optional evidence hygiene checks.** Extend existing `lint` or offer a clearly named report for uncited central claims, unused captured sources, missing review dates for changing facts, and revision gaps—only the checks that can be deterministically established. Don't pretend an LLM contradiction scan of sampled pages is exhaustive. If automated CI wants to fail, add an opt-in nonzero-exit `--strict` rather than changing `lint`'s report-only semantics. [llmwiki reference/lint tooling](https://github.com/lucasastorian/llmwiki/blob/aac3e6493306b7fff3b09cb181ca93918e93d0e6/mcp/tools/search.py); [llm-wiki-agent bounded semantic lint](https://github.com/SamurAIGPT/llm-wiki-agent/blob/572c8eb06e7226567e55a9f186c0860d755a0d51/tools/lint.py).
4. **Use existing document tooling as adapters.** PDF, web clip, chat transcript, audio and Office extraction belong in specialized document/web tools; feed explicitly labeled extracts to `sb capture`. A simple opt-in `inbox/` workflow may help recurring capture, but another embedded converter, browser extension, MCP service, scheduler, Obsidian-only syntax, or vector DB is not justified without a demonstrated bottleneck. [llmwiki browser workflow](https://github.com/lucasastorian/llmwiki/blob/aac3e6493306b7fff3b09cb181ca93918e93d0e6/README.md); [second-brain-os channel guides](https://github.com/undefined-ui/second-brain-os/tree/dcead4dff5cf305c2241d417360730f99fbf7279/docs/03-ingestion).

**Defer:** always-on prompt injection of recalled notes, unattended source-driven rewrites, guessed people dossiers, automatic issue/task sync, comprehensive GraphRAG, many specialist skills/agents, cloud embeddings or a web app. If a bounded recall hook becomes useful, copy its **opt-in, small context, abstain, data-not-instructions** properties, not universal triggering; see [hook code](https://github.com/eugeniughelbur/obsidian-second-brain/blob/b0089f7666d0c1e3db41c9d587b6f3c997665235/hooks/obsidian-recall.py). For graphical views, keep generated graph views disposable and avoid requiring network-hosted JS to read a local vault. For existing pages, preserve our SHA/reason/revision safety instead of replacing it with arbitrary model writes.

## Company brain: a separate product built on the contract, not one bigger personal vault

These repos offer patterns, **not a finished enterprise-brain template**. COG and second-brain-os are single-user instructions; llm-wiki-agent and obsidian-second-brain assume a user's own vault; llmwiki has authenticated hosted personal workspaces but no verified team-shared, source-derived access-control model in the inspected materials. The following is a design recommendation, not a claim any repo implements it.

### Product boundary and representative question

A company-brain user asks *"Why did we stop the Atlas rollout and what is the current owner?"* A useful answer cites the exact incident review and decision, dates the historical answer, obtains **current** ownership from the authoritative tracker (or explicitly declines to claim it), and never reveals a restricted HR or customer document to someone lacking access. A common Markdown vault or an LLM instruction saying "respect permissions" cannot enforce that boundary. [second-brain-os safety guidance](https://github.com/undefined-ui/second-brain-os/blob/dcead4dff5cf305c2241d417360730f99fbf7279/docs/06-agents/safety-and-guardrails.md) puts it plainly: keys, not prompts.

Proposed layers:

1. **Connectors and raw evidence.** Start with one explicitly authorized source, e.g. approved project docs + issues/PRs; later Slack, tickets, incident reports and meeting notes only with owner consent. Preserve source ID/version, URL, capture time, author, document boundaries, extraction provenance and original access policy. Mark records as pointer-only vs locally retained. Sync incremental updates and deletions rather than accumulating invisible stale copies. Source text is untrusted data, never workflow instructions.
2. **Compilation and review.** Agents draft OKF-like Markdown concepts, entities, decisions and topic pages with claim-to-source spans/locations, attribution and `as of`/freshness. Owners approve publication/rewrite for shared canonical pages; dissent and retractions remain visible; maintain exact previous versions and an append-only audit. Fast-changing status lives in its owning system, with a link and observation time in the brain. Store human annotations separately from source text, as [llmwiki's chunk/search model](https://github.com/lucasastorian/llmwiki/blob/aac3e6493306b7fff3b09cb181ca93918e93d0e6/shared/sqlite_schema.sql) illustrates. Sensitive people/CRM notes are not an automatic default.
3. **Identity and enforced authorization.** A first pilot may use a *single homogeneous-access team* and a Git-reviewed Markdown bundle. Mixed-access users require a dedicated identity, space/source policy and query boundary: enforce permissions **before** retrieval, snippet selection, graph expansion, synthesis and citation display. A derived page inherits at least the restrictions of every source supporting its included claims, or is explicitly reviewed/declassified before broader publication; cache/index/export and scheduled briefs obey the same policy. Handle revoke/delete propagation, source retention and redaction *before* ingest. JWT verification (as [llmwiki `api/auth.py`](https://github.com/lucasastorian/llmwiki/blob/aac3e6493306b7fff3b09cb181ca93918e93d0e6/api/auth.py) shows) establishes identity but is not itself document authorization. This is a named company-brain security requirement, not a defect claimed against these personal projects.
4. **Retrieval and feedback.** Begin with policy-filtered lexical search plus navigable cited Markdown. Answer with source links and timestamps; abstain when evidence is missing or stale; allow a subject-matter owner to contest a claim. Evaluate with team-owned questions for correct citations, answer quality, staleness and **unauthorized-result absence**, not only top-k recall. Optional embeddings must use the same policy-filtered candidate set and a permitted local/hosted processing route.
5. **Operations.** Provide an explicit egress and retention policy, audit of connector reads and publication, review queues, source-ACL sync, tenant-safe backups and an offboarding/delete path. MCP/API and a web interface become worthwhile only when multiple agents/people need controlled access. A browser clipper and recurring background jobs are secondary to policy correctness; external write-back to Slack/Linear must require a separate, visible approval. [COG team-brief's differing confirmation points](https://github.com/huytieu/COG-second-brain/blob/4cdb6015dc6eb66f74bac513856ff6446ecb5d1b/skills/team-brief/SKILL.md) illustrate why instructions alone are an incomplete write boundary.

**Reuse strategy:** Keep the personal skill's Markdown/OKF content shape, revision log, source-first method, citations and deterministic lint/index tests. Reuse `sb.py` as a personal tool *until* a concrete multi-user seam justifies extracting shared code; company identity/ACLs, connectors, publication, storage and service belong to a new project. Do not turn `sb.py` into a multi-tenant app via a `--company` flag. Share only explicitly approved/public knowledge between personal and company bundles, never symlink private content into a shared vault. A Git-based same-access pilot should precede any Postgres/S3/MCP deployment; a hosted backend is a possible later implementation, not a prerequisite or a transplant of [llmwiki's local/hosted architecture](https://github.com/lucasastorian/llmwiki/blob/aac3e6493306b7fff3b09cb181ca93918e93d0e6/README.md).

### Decisions to make before a company specification

- Who is the first reader group, what material may it see, who can publish or correct, and which source-of-truth systems are in scope?
- Are there mixed-permission documents or regulated/personnel/customer data? Which processing/hosting locations and model providers are allowed?
- Which answer scenarios matter enough to seed a retrieval/citation evaluation, and what is the expected freshness for each source?
- Will the first pilot be a reviewed same-access Markdown bundle, or must it serve mixed-access readers from day one? The latter changes the architecture immediately.

**Suggested sequence, pending explicit approval:** (1) trial the answer contract and capture provenance in the personal skill; (2) measure real retrieval misses, then select one CLI improvement; (3) write a separate company-brain specification from the reader/ACL/source decisions; (4) pilot one source with approval and policy-aware evaluation. Research acceptance alone is not authorization to implement.
